# How we work

The language owner, the maintainer and a team of builders build PHP#. This file says how the team works. The maintainer owns it, and it changes only through a PR, so git keeps its history.

## Who does what

- **The language owner** decides the language: `docs/spec.md` and the proposals in `docs/decisions/`. The language owner approves or corrects proposals, and doesn't review code or plan work.
- **The maintainer** owns everything else: the plan, the order of work, the architecture, and this file. It starts every agent, reviews each task's architecture and capabilities before it starts, and checks that what lands meets its Verification.
- **A builder** is an agent that does one task: one PR, from a new branch to its approval.
- **A helper** is an agent that reads, searches or researches for the maintainer, and changes nothing.

## A PR's path to master

No agent reviews code. The review happens before the code exists, and the check after it is the task's Verification.

0. Before the maintainer founds the builder, it reviews the task's architecture and capabilities: every file and public API it changes, every capability it must keep, and the Verification that proves it. Verification names each case where the change could give a wrong result, a crash or a cost, as an input and the output it must give, in every mode CI runs. It is the check a code reviewer would have made.
1. The builder builds the task on its own branch `issue/<number>` off master, in its lane's own worktree, and opens the PR into master with auto-merge on. CI must pass, and its report shows each Verification condition met, with the command and the output it observed.
2. The maintainer checks that Evidence against each condition, and checks the PR's shape against the task: the files and public APIs it changes, and no stopgap. A miss goes back to the same builder, and the maintainer checks its fix the same way.
3. When every condition is met, the maintainer posts an approval on the PR.
4. The queue lands it (#843). `queue.yml` merges every ready PR onto master's tip, oldest first, and pushes the result to `staging`, whose run runs every check, the Mac's among them, on the tree that will land. `LAND` then moves master to that commit with a fast-forward and starts `queue.yml` again, which starts the next batch's run, and `release.yml`'s release of master's tip when it is due, as the release's path explains. A PR is ready once its auto-merge is on and its own run passed the required checks. `master merge gate` also requires `QUEUE`, a check no run ever reports, so GitHub never merges a PR itself, and auto-merge stays the signal that a PR is ready. `LAND`'s push with the deploy key, which the gate lets past, is the only way onto master, and `master history` refuses any force-push or deletion of master. GitHub's own merge queue is offered only to repositories an organization owns, and this one is a user's.
5. A staging run that fails leaves master where it was. A batch of several PRs then takes its oldest PR alone, so one broken change never holds the others. A PR whose staging run failed with it alone gets a comment naming the run, and waits until its head moves. A PR that conflicts with master or with a PR merged ahead of it gets a comment and stays out of the batch.

A commit that finishes spec sections says so in its message, on its own line, exactly as `Completes: §6.1, §9`, so the PR that lands it checks the claim. The `COMPLETES` check fails while `sharp/baseline/spec` still lists an example of a named section.

A feature PR changes the spec, its examples, `sharp/baseline/spec` and the code together. It leaves `sharp/bin/spec`, which measures the examples, as master has it: that changes only in a PR of its own, beside Markdown. A feature PR may add or change harness classes in `sharp/harness/`. Its body lists each harness file, and its Verification proves that no stub makes an example pass falsely. When the builder's work makes listed examples pass, the failing run prints the `git rm` of each fixed example's file in `sharp/baseline/spec/`, and the entries leave through it. A listed example that fails with other errors than before stays on the list unchanged, because the list records which examples fail, not how. An example master already checked never joins the list unchanged.

New example-marker or run-comment syntax lands in `sharp/bin/spec` one PR before the examples use it, because `SPEC_GUARD` reads a PR's spec with the base's checker.

One feature is one PR: the checker in `sharp/mago/`, the engine, the standard library, the spec and their tests change together, and every CI gate runs on it.

A PR is ready to land when its own required checks pass: `CI_PASSED`, `SPEC_GUARD` and `COMPLETES`. One workflow, `sharp.yml`, runs every check of a commit, Mago's among them, under one `CHANGES` job and one gate, `CI_PASSED` (#853). Each Linux suite runs in slices, `LINUX` and `SPEC` in 2 and `MAGO` in 3, and `UPSTREAM_AND_HOSTS` as one job (#957), and GitHub runs 20 of the account's hosted jobs at once, across all its repositories. A PR's own run skips `MAC_TESTS` and `IMAGE`, whatever the PR changed, since its tree never lands, and the staging run runs them on the tree that does. No PR's run builds the release, since a PR's run only has to prove the tree compiles and passes its checks, which its test builds do: while a bump waited on `next`, the branch every lane pushed to before #722, every run there built the profile-guided release, and run 44997846679 took 45 minutes, 16.5 of them the release build alone after its checks had ended. A PR that is behind master but has no conflict lands without an update: its staging run tests it merged onto master and the PRs ahead of it, which is the tree that lands.

Each platform builds once per run, and the suites of that platform wait for that build and run on it. `sharp.yml`'s `BUILD_MAGO_ENGINE` builds the engine `mago` links on the runner's Ubuntu 24.04, whose glibc is older than the `sharp/docker` image's, for `MAGO_CHECKS`, which runs Mago's gates and builds the test-run `mago` that `PLAIN_PHP` and `SPEED` run. `BUILD_LINUX` builds its own engine, `mago` and the workspace's test binaries in the image (#955), and each suite, `MAGO`'s slices of Mago's tests among them, takes their files with `sharp/bin/test --no-build`. A staging run has one Mac job, `MAC_TESTS`, on the Mac's one runner: it builds the debug engine once, and runs every test there. This reverses the earlier rule that no job waits for another job's build: each job built for itself so that no build's minutes stood before every suite, but a release's version bump rebuilt every Mago crate in every one of them, and release PR #363's run built the same code in 8 Linux jobs, 4 jobs of Mago's own workflow and 3 Mac jobs, 238 of its 404 job-minutes on the three Mac runners. One build per platform costs its minutes once, before the suites, and frees the runners the copies held.

Every staging run runs one job on the Mac's runner: `MAC_TESTS`, which runs the PHP# suite, Mago's workspace tests and `plain-php` there. It runs every test the Linux jobs run, `tests/laws.rs` and the whole-project proof of `mago convert` among them, but three that can't run on macOS: the JIT, since Apple silicon has no thread-safe JIT, the upstream tests, whose baseline holds Linux's results, and `sharp/bin/hosts`, which builds FrankenPHP in the `sharp/docker/` image. Only a staging run builds the runtime image, in its `IMAGE` jobs. Each PR's run is in a concurrency group of its own, where a newer push to the PR cancels its run in progress, and a PR's run runs every job to its end, so one run reports every failure. Each staging push's run is in a group of its own too, and `queue.yml` pushes `staging` once every staging run has landed. A failed job cancels its staging run, which can no longer land, so `queue.yml`'s next batch and the Mac take its place. Every run builds and tests everything from source, with no cache and no result of an earlier run, so a run's length is what building and testing PHP# costs (#721): a PR's run runs every Linux check, and a staging run every check, the Mac's among them, so each landed tree crosses the Mac once. #828 crossed it twice, in PR run 45570037780 for 55 minutes, then in master's push run 45600915642 for 87 (#843). `ASAN` runs nightly, so a memory error only AddressSanitizer finds lands on master, and the nightly run finds it.

Each change lands alone (#722). Every lane pushed untested commits onto one shared branch, `next`, and one broken commit turned every later one red, so no fix landed until it was fixed: on 2026-11-23 one CI image commit kept `next` red for over two hours. Now each issue is its own branch and PR, and the queue tests each change merged onto master with the changes ahead of it in its batch, so master stays green, and a broken change fails its batch, then its own, while the changes behind it go on. A PR starts the required runs because its builder opens it with the language owner's `gh` login, where one that `GITHUB_TOKEN` opened would start no workflow. A change to `sharp/bin/spec` reaches master in a PR of its own.

A red staging run opens one issue, or comments on the one still open, with the range of commits it tests, and master stays where it was. A PR fixes it forward, and other PRs keep landing. A release publishes only a tree a full run passed, as the release's path explains.

## A release's path

`queue.yml` starts `release.yml`'s run of master's tip once a staging run landed: at once when no PR waits to land, or once 3 landings since the newest public release are unreleased. It starts none for a tip a tag names, and none when `sharp/bin/release-notes` prints the same for the PRs master holds since the newest public release as for none, its empty case, since none has a `## Changelog` entry (#1125). No commit and no file in the tree names a version: the version lives in its tag, and the tree's root package `mago` stays `0.0.0`. Nobody tags or publishes by hand. The `release` group keeps one release run in progress and one waiting, and a newer run waiting replaces the older one, so a release of the newest landed tree ships every landing before it.

1. `release.yml`'s `VERSION` runs `sharp/bin/check --release`, which finds the version. A commit a tag already names keeps that tag's version, so a later run finishes its release. Any other commit takes the newest tag's version plus one patch, so an untagged draft's version goes to the next run, or one minor when the title of a PR the commit holds since that tag has `!` before its colon. `sharp/bin/check --release '<title>'` adds a title, which is a dry run of the version.
2. The run builds the release's files once: `crate_metadata` writes the release's notes, `source_archive` Mago's source archives, `build` the three `mago` binaries, each on a runner of its own platform with its attestation, the macOS one with profile-guided optimization from `profile.yml`'s `mago-profile` artifact, and `sums` their SHA-256s. Each job that builds writes the version into its checkout with `sharp/bin/set-version` first. Each attestation names the run's commit. `IMAGE` builds the runtime images through `image.yml`, with the version written the same way.
3. The notes are the `## Changelog` section of each PR the release holds since the newest published release, so a release after a tag whose release never published carries that tag's PRs too, its lines under their `###` headings, with `### Upgrading` first when users rewrite code. The template in `.github/pull_request_template.md` holds the section. The list of releases on GitHub is the changelog.
4. `RELEASE` runs only when every job before it passed, a job past its timeout counted as failed, and checks each asset against its SHA-256, its attestation and the release's tree. It uploads the assets to an untagged draft GitHub release that targets the run's commit. `PUBLISH` then checks each image digest against the release's tree and makes the release public, which creates tag `v<version>` on the run's commit in the same call, and tags the images `<version>` and `<major>.<minor>`, each with its `-dev` image. Last, `COMPOSER` pushes tag `v<version>` of the release commit's split to `heyJordanParker/php-sharp-composer`, with that commit's spec, and to `heyJordanParker/mago-sharp` with the release's SHA-256s and version, so Packagist lists a version only once its release downloads. A run that fails before `PUBLISH` leaves an untagged draft and nothing public, so the next release run takes the same version, and a published tag never moves (#854). A failed release job opens the red-master issue from `red_master_issue`, and is fixed forward.
5. A release publishes three parts: the GitHub release with `mago`'s files, the runtime images, and the Composer tags. `sharp/bin/check --release` prints which are missing, and a release run publishes only those, so a published part stays as it is.

## Every mistake becomes a check

Agents make mistakes, and a rule written only in prose gets broken again. So when the maintainer or CI finds a mistake, the fix comes in two parts:

1. Fix the mistake.
2. Add the check that would have caught it: a test, a lint, a CI step or a Claude Code hook. The check fails on the mistake and passes on the fix, and the PR shows both runs.

A mistake that no check can catch yet goes in `docs/architecture/guards.md`, with what a check for it would need. Each entry becomes a task, and it runs before any new feature work in the same area. Until `docs/architecture/guards.md` exists, the maintainer writes each such mistake straight into a task file.

## Test runs

- A PR runs each PHP# engine mode once, on the one engine PHP# ships, the thread-safe one FrankenPHP runs, in the configurations deployments run. Linux runs plain PHP, opcache shared memory twice per process and the tracing JIT, 3 modes. Every staging run also runs the first 2 on macOS, where Apple silicon has no thread-safe JIT. No job runs the suite on arm64 Linux: macOS on Apple silicon runs the arm64 code, and x86_64 Linux the Linux code, and the arm64 runtime image shows that its engine starts and loads PHP#. Every night, master runs the 3 modes on Linux under AddressSanitizer. A PR can't land until its own runs and its staging run pass. Every PR runs them, whatever it changed.
- Every build and test runs at most as many jobs as `sharp/bin/jobs` prints, 6 on the builders' Mac, which has 12 cores and 64 GiB and runs other builders' work beside them. `CARGO_BUILD_JOBS` sets another number: the Mac's runner sets it to every core of its Mac, since it runs one job at a time.
- One `sharp/bin/test` runs per worktree at a time, and each run of it and of `sharp/bin/bench` stands on its own:
  - `sharp/bin/bench` compiles a copy of its rows inside its own container, so it runs beside `sharp/bin/test` in the same worktree. The exception is `sharp/bin/test --linux`: it and `sharp/bin/bench` build `mago` in the same `sharp/build/linux-<arch>/mago/`, where either one's `sharp/bin/build-mago` can delete the `mago` the other runs, so they don't run at once.
  - A run that failed or was stopped leaves nothing that breaks the next one.
  - Every `sharp/bin/test` mode, `--linux` included, works the same in a git worktree as in the main checkout.

## Platforms

PHP# supports macOS on Apple silicon, for development, and glibc Linux on arm64 and x86_64: the Linux VMs on the Mac and the Hetzner servers. CI and releases build for those only.

## Where things are written

- `docs/spec.md`: the language, as the language owner approved it. CI compiles and runs its examples, and `sharp/baseline/spec` lists the ones that fail today, which is the distance to v1. Git keeps no empty folder, so when none fails the folder is missing, and `sharp/bin/spec` reads a missing folder as an empty list.
- `docs/decisions/`: each approved language proposal, with the options it chose between.
- `docs/architecture/`: how the checker and the engine are built, and why, once the change lands on master.
- `~/Developer/php-sharp/sharp/agents/architecture.md`: the architecture of the change in flight, which the maintainer writes for builders. Git ignores it, and it moves into `docs/architecture/` with the PR.
- `docs/how-we-work.md`: this file.
- `~/Developer/php-sharp/sharp/agents/`: task files. Git ignores them, so they exist only in that checkout.
