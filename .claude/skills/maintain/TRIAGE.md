# Triage

Move every reported problem through a small state machine of labels on the php-sharp issue tracker. A problem from another agent, a consumer project, CI, a builder or the language owner becomes an issue before any work starts.

## Write it into intake first

Every problem enters `~/.claude/orchestrate/php-sharp/intake.md` as one entry the moment it arrives, before an issue, a brief, a dispatch, a proposal or a word to the language owner. The entry is a checklist, and each box is checked only with what it asks for written beside it:

```markdown
## <the problem, as what a PHP# program does today>
source: <who hit it, and where>
- [ ] issue: #<number>
- [ ] verified: `<command>` on the released mago gives <output>
- [ ] root cause: <the function and lines a run of the repro shows emitting the refusal or the wrong value, MM-DD>
- [ ] outcome: brief | wontfix | needs-info | proposal
- [ ] design: `proposals/<slug>.md` holds PROPOSE.md steps 1 to 3, never the reporter's request, and a `## Facts` section of `- <claim>: \`<command>\` prints <output>` lines that `facts.py` reruns
- [ ] precedent: the system's one in `precedents.md`, each departure's reason
- [ ] consistent: the same-kind names, commands, flags or outputs beside it, matched
- [ ] request: (from another agent) the design's `## Request`: each item it asked for as `kept: <precedent or neighbor>` or `dropped: <why>`
- [ ] proposal: today's program compiled, and the change attacked per PROPOSE.md step 4
```

The intake file is the maintainer's one queue, the language owner's requests included. An entry goes in at its rank from SKILL.md section 4, a red check or a `blocking` problem first. One entry at a time carries `(in progress)` in its heading, and it is worked through every box before the next one starts. Only a red check or a `blocking` fix that is green and not yet released goes ahead of it, and the paused entry's heading says where it stopped. An entry whose next box waits on a builder's run or the language owner's answer is marked `(waiting on …)`, and the next entry by rank is worked meanwhile.

The design box applies to every brief or proposal that makes an architectural call, the maintainer's own included, and the proposal box only to a `ready-for-human` change to what a PHP# program says or means. CI, tests, speed, releases and the process are the maintainer's, decided in the design box and never proposed. An entry leaves intake when every box that applies is checked, and only then is its brief posted, its builder dispatched or its proposal shown. A reply names an entry still in intake by its problem and the next box it needs, never as a decision for the language owner.
Never: a problem shown to the language owner, briefed or dispatched with a box unchecked.

Every comment the maintainer posts during triage starts with:

```
> *This was generated by AI during triage.*
```

## Labels

Two **category** labels:

- `bug`: something is broken
- `enhancement`: a new capability or an improvement

Five **state** labels:

- `needs-triage`: the maintainer has to evaluate it
- `needs-info`: waiting on the reporter for a repro
- `ready-for-agent`: verified and briefed, ready for a builder
- `ready-for-human`: a change to what a PHP# program says or means, which the language owner decides
- `wontfix`: will not be built

One **priority** label:

- `blocking`: it stops a consumer or user today, so a release is cut the moment its fix is committed. A problem in PHP#'s own build, CI or process ranks as a red check, never `blocking`

Every triaged issue carries one category and one state label, and starts at `needs-triage`; `needs-info` returns there once the reporter answers.

## Triage one problem

A question about how to use PHP#, an audit of a consumer's own rules, or a request to pick a form for a consumer's code is not a problem. It gets no issue and no answer, because the spec answers it and the maintainer's time goes to PHP#. Only a defect, with a repro, a missing capability, or a speed target off its goal enters triage. A defect enters only when a project, a user or CI hit it. A defect a builder or a tool found by exploring, which nothing hit, gets no issue.

The language owner's feedback is a problem like any other: it runs all five steps, and a builder gets the Solution the maintainer designed from the code, never his words.

A speed target off its goal is a problem like a defect a consumer hits, and ranks with one. Its entry's heading is `## Speed: <target>`, as the hook names it. Step 2 searches `benchmark/experiments.md` for the same change, and a design that repeats a dropped line needs a new reason, which its design file states. Step 3 verifies it by its count: the frozen project's, as `benchmark/speed.php` counts, or the last green run's job timeline. Step 4's root cause is the function or the step that a profile of that count shows costing most. Its brief makes that work cheaper, and once it is briefed, the next cost enters as a new entry. Every verification loop, a local build, test or measure or a CI job, ends within 5 minutes, since an agent can't debug a longer one, so the longest local loop and the longest CI job are speed targets, and a long loop is broken into parts that each end in a check. Each kind of loop over 5 minutes in the build log or the last green run is its own entry at once, never one after another. A design may rewrite a core part of the engine or of Mago, generally in Rust, behind a compatibility layer.

Run all five steps on the entry in progress before starting another. Filing is only step 1: nothing else in the loop verifies an issue left at `needs-triage`.

1. **File it.** The issue states the problem as behavior: what a PHP# program does today, and why that's wrong. The tracker is public, so the issue never names a consumer project, its files or its people. Its repro is a generic program that shows the same failure, renamed from the shapes the consumer's agent sent. The maintainer never reads the consumer's code, and consumer source an agent sends stays in the scratchpad.
2. **Check that it's new.** Search the code for the capability by its concept, not the report's wording, and search open and closed issues. A problem with the same root cause as an open issue joins that issue, and the newer of the two closes as its duplicate. If PHP# already has the correct form, close the issue as `wontfix` with that form shown as code. A consumer project is a measurement, never a source of features: its feature request is built only when it is good for PHP# on its own, because it solves several problems, it helps agents write better code, and PHP# has no form for it today. Otherwise the consumer restructures on its side.
3. **Verify the claim.** Reproduce it: a command that fails today, or a test that goes red. Run the repro with the latest released `mago`, downloaded from its GitHub release into the scratchpad, never the shared target's build, which may be stale. A probe project's `composer.json` says `"type": "library"`, so the rules for applications stay out of the result. Record what happened: confirmed with its code path, failed, or not enough detail for `needs-info`.
4. **Decide the Solution.** Find why the failing state can exist at all, from first principles, before any fix: a report names a symptom, and a member or function that handles a state PHP# should make impossible treats that symptom. Write the same failure for a second type, caller or layer the rule spans: when another one fails too, the root cause is the rule they share, and a Solution that names one type, caller or format is a patch. Check the Solution against the intent of each ruling it touches, read from the rulings record, and never take the reporter's or the language owner's suggested fix as the design without that check. Read the code the change reaches: the function that resolves it, its callers and the tests beside it. List each way a program builds a value the rule covers, such as its constructors, moves, `Json.decode`, reflection and defaults, and check the design against each. Decide the Solution, every public name it adds, every consumer it reaches, and every file it changes, so the builder builds once and its lane is known before dispatch. The root cause names the function and the lines that make the failing state, read this turn, and each claim about what reads a file is checked by finding every reader. The brief names every check a red CI run would otherwise find, such as each engine mode for an engine change. A rule has no exemptions. A report that a rule fires wrongly is either a bug in the rule, fixed in the rule for every program, or a correct refusal that stays. The fix the reporter asks for is never the default Solution. Pick the one that keeps the correct way the only way: often no change to PHP# and a restructure on the consumer's side, never an escape hatch or a second way that an agent could misuse. A Solution never adds a fallback attempt, a cache, a skip or a check that decides whether to run a test, since each is a second path and a failure of its own, and it never asks a PHP# project to hold a plain PHP file. A Solution that changes what a PHP# program says or means goes to `ready-for-human` instead.
5. **Apply the outcome:**
   - `ready-for-agent`: post the brief, per [AGENT-BRIEF.md](AGENT-BRIEF.md), with its `**Verified:**` and `**Root cause:**` from steps 3 and 4. A bug without both stays `needs-triage`, whoever reported it and whatever fix they proposed.
   - `ready-for-human`: the issue holds the problem and what was verified. The proposal goes to the language owner in the conversation, per [PROPOSE.md](PROPOSE.md), and the issue gets the brief only after his ruling.
   - `needs-info`: post what is established and the specific questions left.
   - `wontfix`: close the issue with the reason, and with the correct form when one exists.
